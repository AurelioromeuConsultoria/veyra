# DOMAIN_MODEL — Veyra Core

Modelo inicial. Nomes de entidades em inglês (código), descrições em pt-BR. Nada aqui é migration ainda — o schema Prisma só nasce na Fase 2.

## 1. Convenções

- IDs: `String @id @default(uuid()) @db.Uuid`.
- `createdAt @default(now())` + `updatedAt @updatedAt` em tudo. **Exceção** (ADR-049): instante que o banco compara com `now()` é escrito pelo banco. Hoje são o `OutboxEvent.nextRetryAt` e o `MessageDispatch.updatedAt`, que usam DEFAULT e trigger.
- Toda entidade de domínio: `workspaceId String @db.Uuid` obrigatório, relação com `Workspace` com `onDelete: Cascade`, índices compostos liderados por `workspaceId` (`@@index([workspaceId, ...])`), uniques tenant-scoped (`@@unique([workspaceId, ...])`).
- Toda entidade referenciável por outra entidade de workspace declara `@@unique([workspaceId, id])` para permitir **FKs compostas** (`FOREIGN KEY (workspaceId, xId) REFERENCES X(workspaceId, id)`) — impedindo relações cross-tenant no próprio banco.
- Dinheiro: `Int` em centavos + `currency` (ISO 4217).
- Sem soft delete genérico; `archivedAt`/`status` onde fizer sentido; exclusão LGPD via cascade a partir de `Workspace` (e de `User` para dados globais).

A timeline de um contato/deal é a consulta de `Activity` pelos FKs explícitos — auditável e tenant-safe. Desde a F4.1a (ADR-052, C12), a do contato soma, às atividades com o `contactId` gravado, as atividades sem contato das conversas que hoje são dele: a atribuição de mensagem vem da conversa, e uma conversa rejeitada sai da timeline sem apagar nada.

## 5. Comunicação

Implementado na Entrega 6.1 (ADR-023). A API aceita **somente** canal `internal`; `email`/`whatsapp` estão reservados no enum, sem provider.

| Entidade          | Campos-chave                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Notas                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Channel`         | type (internal/email/whatsapp), name, **systemMark** (TRUE/NULL)                                                                                                                                                                                                                                                                                                                                                                                                              | Exatamente **um** canal interno por workspace: `@@unique([workspaceId, systemMark])` + CHECK (`systemMark` só TRUE, e só em `internal`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `Conversation`    | channelId (FK composta), contactId? (FK composta), subject?, status (open/pending/closed), assigneeMembershipId? (FK composta), **lastMessageAt NOT NULL**, externalAddress?, senderStatus (identified/unidentified — ADR-052), senderIdentifiedAt?, openMark e unidentifiedOpenMark (por gatilho)                                                                                                                                                                            | `lastMessageAt` já nasce preenchido — o keyset do inbox `(lastMessageAt, id)` não tem caso especial de null. Mensagem em conversa fechada a reabre, exceto se já houver outra aberta da mesma chave (409). Uma conversa aberta por (canal, contato, número) e uma RAI aberta por (canal, número), garantidas por único com as marcas. A RAI ("remetente a identificar") nunca tem contato (CHECK), não recebe resposta, e só o serviço de identificação muda `contactId`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `Message`         | conversationId + channelId em **FK TRIPLA** `(workspaceId, channelId, conversationId) → Conversation(workspaceId, channelId, id)` — o canal da mensagem é obrigatoriamente o da conversa; `channelId` é derivado da conversa no servidor, direction (inbound/outbound), authorType, authorMembershipId?/authorContactId? (FKs compostas; desde a F4.1a, a mensagem nova não grava `authorContactId`: a atribuição ao contato vem da conversa), body, deliveredAt, externalId? | **Append-only** (`APPEND_ONLY_MODELS`). `@@unique([workspaceId, channelId, externalId])` para dedup de ingestão; `externalId` é id de OUTRO sistema, exceção documentada no `check:fk`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `MessageDispatch` | messageId (PK e FK composta para a mensagem), state, reservationId, leaseExpiresAt + claimToken (posse com fencing), dispatchedAt (marcador de despacho), template pedido, externalId, errorCode, attempts, **approvalContactIds** (uuid[]), **fromAiProposal**                                                                                                                                                                                                               | O envio pelo canal externo (ADR-039). `approvalContactIds` são os contatos conferidos por quem APROVOU o envio: na aprovação do rascunho da IA (ADR-047 adendo 7 §9, G3.2), o envio da IA trava e reconfere todos eles, somados ao contato atual da conversa, sob a guarda de uso externo; na mensagem escrita por pessoa (ADR-052, revisão da F4.1a), é o contato da conversa quando ela escreveu. Nos dois, o worker não envia se a conversa tiver sido religada desde então (`conversation_relinked`). Como a RAI não recebe resposta, toda mensagem na fila foi escrita para um contato. Sem FK, validados na escrita e conferidos pelo `check:fk`. `fromAiProposal` é a ORIGEM DE IA: o despacho nasceu da aprovação de uma proposta da IA, editada ou não, e sai sob a restrição e a guarda como o da IA, mesmo com `authorType = 'user'` (decisão de 2026-10-21). Em dúvida, o despacho fica `unknown_after_dispatch` e nunca é reenviado; quando a guarda provou que ele não saiu, o código é `not_sent_guard_aborted` |

O autor é **derivado da direção**, nunca informado pelo cliente: `outbound` → membership da sessão; `inbound` → contato da conversa (conversa sem contato recusa entrada). O envio manual é `@Idempotent()`: duplo clique não duplica mensagem nem `Activity`.

Timeline: `Activity` ganhou `conversationId` (FK composta) e os tipos `message_sent`/`message_received`, com **payload vazio** — o corpo da mensagem nunca entra na timeline.

## 6. Organização

Agenda e notificações implementadas na Entrega 6.2; arquivos entram na 6.3.

| Entidade        | Campos-chave                                                                                                                                                                 | Notas                                                                                                                                                                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CalendarEvent` | title, description?, startAt, endAt, location?, status (scheduled/done/canceled), organizerMembershipId, contactId?, dealId? — **todas as relações em FK composta**          | **CHECK `endAt > startAt` no banco**, além do Zod. Emissão de notificação acontece **dentro da transação do fato que a origina** — notificação de evento que não existe é impossível. Hoje há dois produtores: evento agendado para outra pessoa e conversa atribuída a outra pessoa. ## 9. O que NÃO é modelado (deliberadamente)

- Qualquer conceito vertical: paciente, prontuário, imóvel, visitante, matrícula, apólice.
  Os modelos de um vertical ficam no arquivo de schema dele (`prisma/schema/<vertical>.prisma`) e são documentados no ADR do vertical (Clinics: ADR-048 e adendo 3 do ADR-047). O arquivo do Core só cita esses modelos como lado reverso de relação (`ClinicsContactRelease[]` em `Contact`, por exemplo), exigência mecânica do Prisma guardada por teste.
- Role global ou "super-admin de produto" no modelo de tenant (operação administrativa é rotina `raw` justificada, fora do RBAC de workspace).
- Relações polimórficas sem FK (`entityType + entityId` soltos) — exceto `CustomFieldValue` e `AuditLog`, que são tenant-scoped, não navegáveis e existem exatamente para isso.
- Event sourcing, CQRS, filas distribuídas.
- Registro público de usuário.

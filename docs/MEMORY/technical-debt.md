# Dívida técnica — aceita conscientemente, com gatilho para resolver

Regra: dívida entra aqui com o motivo e o **gatilho** que obriga a resolvê-la. Resolvida = remover a linha.

| Dívida                                                                                                                                                                                     | Por que foi aceita                                                                                                                                             | Gatilho para resolver                                                                                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Oráculo de timing no aceite de convite (bcrypt roda só com token válido + conta existente)                                                                                                 | Atacante relevante já sabe que o token é válido; vazamento desprezível no modelo atual                                                                         | Verificação de e-mail no aceite (pós-MVP) — adicionar `compare` dummy junto                                                                                                                 |
| Advisory lock de membros usa `hashtext` (int4) — colisão entre workspaces gera contenção rara, nunca ausência de lock                                                                      | Simplicidade; over-serialization é inofensiva                                                                                                                  | Contenção medida em produção → migrar para chave bigint de 64-bit                                                                                                                           |
| Aceite de convite para e-mail SEM conta cria a conta (pré-registro possível pelo convidante, restrito ao workspace dele)                                                                   | Sem serviço de e-mail ainda; sem pivô cross-tenant                                                                                                             | Canal de e-mail real (Entrega 9+, depois do WhatsApp) → token deixa de retornar ao criador + verificação de e-mail                                                                          |
| Permissões checadas por query a cada request (PermissionsGuard)                                                                                                                            | Simplicidade; volume baixo no MVP                                                                                                                              | p95 do guard > 20ms ou 1k req/min sustentado → cache por (roleId, updatedAt)                                                                                                                |
| `vendor-form` (Zod + RHF) = 443 kB no carregamento inicial: sem tree-shaking porque `@veyra/contracts` é CJS e o Login importa o barrel inteiro                                            | Splitting por rota já resolveu o app (26 kB) e as páginas (3–58 kB); mexer no build do contracts afeta a API em produção                                       | Chunk inicial precisar cair de ~700 kB: build dual ESM+CJS no `@veyra/contracts` com `sideEffects: false` (+ medir com `vite build --analyze`)                                              |
| `update`/`remove` de deal não emitem Activity (timeline cobre criação e movimentação, não alteração de valor/dono nem exclusão)                                                            | Sem AuditLog ainda (Entrega 5), que é o lugar certo do "before/after"                                                                                          | **Entrega 5**: AuditLog com allowlist entra e cobre o histórico de alteração                                                                                                                |
| `createNoteSchema` aceita vários alvos enquanto `listNotesSchema` exige exatamente um                                                                                                      | Assimetria sem impacto de segurança; nota com 2 alvos aparece nas 2 listas                                                                                     | Padronizar em "exatamente um" ao mexer em notas (Entrega 6, inbox)                                                                                                                          |
| `removeStage` não valida a invariante "≥1 stage `open`" no pipeline                                                                                                                        | Precheck de stage ocupado já existe; pipeline sem stage open só quebra criação de deal (400 claro)                                                             | Ao permitir templates de pipeline por vertical (pós-MVP)                                                                                                                                    |
| `Timeline.tsx` ignora `nextCursor` (mostra 30 eventos, sem "carregar mais")                                                                                                                | Keyset pagination pronta e testada no servidor; UI mínima na entrega                                                                                           | Deal/contato passar de 30 eventos em uso real → `useInfiniteQuery`                                                                                                                          |
| Exclusão de contato com deal/tarefa retorna 409 genérico (sem precheck com contagem)                                                                                                       | O 409 do filtro P2003 evita 500; caminho raro no MVP                                                                                                           | **Entrega 5/LGPD**: precheck com mensagem específica + ADR de erasure (anonimizar vs. bloquear)                                                                                             |
| `DEFAULT_STAGES` mora em `apps/api` e é importado pelo global-setup do e2e                                                                                                                 | Constante de domínio usada por API, migration, fixtures e e2e                                                                                                  | Mover para `packages/contracts` ao tocar em pipelines de novo                                                                                                                               |
| Mídia recebida consome storage **sem barrar** (`consumeOverLimit`): um contato pode empurrar armazenamento acima do plano, 10 MB por item, sem teto de contagem                            | Coerente com "quota esgotada não descarta mensagem de paciente" (§7.9); barrar aqui perderia anexo clínico por limite de plano                                 | Billing real ou primeiro abuso observado → teto de contagem por conversa/dia no canal externo, com o excesso visível no medidor                                                             |
| `FileObject` de canal externo é atribuído à membership ativa mais antiga (`systemUploader`) e não gera `AuditLog`: exame enviado pelo paciente aparece como enviado por uma pessoa         | A coluna é NOT NULL e o DTO a expõe; tornar nullable é migration + contrato + front                                                                            | **Antes do piloto Clinics** (pergunta de LGPD "quem manipulou este arquivo?" tem consequência clínica) → coluna nullable + ator de sistema explícito + `AuditLog` com `actorType: 'system'` |
| Teto de plano **não é aplicado** sem `Subscription` ativa (`limitsFor` devolve vazio → limite nulo): workspace `past_due`/`canceled` envia WhatsApp sem limite                             | Pré-existente; `messages_sent` é a primeira métrica com custo real do outro lado, então o controle de plano deixa de existir justamente no inadimplente        | **Decisão de produto pendente** (bloquear WhatsApp por inadimplência é escolha de negócio): fail-closed com teto do plano-base, ou fail-open declarado. Gatilho: entrada de billing         |
| Envio com anexo no canal externo é recusado em 400 (o transporte não manda mídia)                                                                                                          | Recusa explícita é melhor que 201 com anexo perdido; hoje o `scanStatus: pending` já barraria antes                                                            | **Entrega 9.2**: com o scanner ligado, implementar envio de mídia pela Graph API                                                                                                            |
| Falha intermitente NÃO reproduzida na suíte de envio (um bloco de testes que asseveram envio real falhou com `transport.sends` vazio; 6+ rodadas seguintes limpas, banco recriado do zero) | Causa não identificada — registrada em vez de inventada; a asserção agora imprime estado do dispatch e contador, então a próxima ocorrência se explica sozinha | Segunda ocorrência → investigar com o diagnóstico em mão; enquanto isso, rodar a suíte de integração duas vezes no CI antes de confiar no verde                                             |
| Envio pode ficar **entregue e não cobrado**: se o processo morre entre concluir o dispatch e liquidar a quota, a reserva órfã é devolvida pela purga e nada mais a encontra                | Deliberado (ADR-039, trade contra cobrança dupla); a direção do erro favorece o cliente e o volume é o de mortes de processo                                   | Primeiro workspace em cobrança por consumo → reconciliação periódica: `MessageDispatch` em `sent`/`unknown_after_dispatch` sem consumo correspondente no período                            |
| `MessageDispatch`, `MessageStatusEvent` e `InboundMedia` crescem sem retenção; a varredura de dispatch abandonado usa limiar fixo de 15 min                                                | Volume proporcional ao tráfego de WhatsApp, baixo no piloto; o dispatch é a trilha de "o que aconteceu com esta mensagem", útil justamente por um tempo        | Primeiro workspace com volume real de mensagens → retenção junto do expurgo de `AuditLog`, e limiar da varredura vindo de configuração                                                      |
| `IdempotencyKey` e `WebhookDelivery` sem job de expurgo (tabelas crescem); `Activity` sem retenção                                                                                         | TTL/lease já evitam bloqueio funcional; volume baixo no MVP                                                                                                    | Primeiro cliente com volume real → job diário de expurgo + retenção de Activity                                                                                                             |
| `AiRun.result` guarda conteúdo derivado de conversa e não entra na rotina de retenção (só `AuditLog` tem expurgo)                                                                          | Volume baixo e o dado é do próprio workspace, coberto por consentimento e isolamento                                                                           | **Entrega 9.2**: retenção de `AiRun.result` entra junto da privacidade operacional                                                                                                          |
| Reserva de custo de IA é pessimista: usa o teto de tokens, então rajadas de runs baratos podem bater no limite antes do gasto real chegar lá                                               | A liquidação devolve a sobra logo após cada run, mantendo a distorção curta; o alternativo (cobrar depois) não protege teto algum                              | Reclamação real de teto atingido cedo → estimar entrada por tokenização de verdade em vez de caracteres                                                                                     |
| Teto de 20 webhooks/workspace é checado com `count()` antes do `create` (não é atômico)                                                                                                    | Duas criações simultâneas podem passar com 19 e resultar em 21; o heartbeat do lease continua protegendo a entrega, então não há risco de duplicação           | Concorrência real na criação de webhooks (ou teto usado como limite de plano/billing) → reserva atômica: unique parcial por posição ou advisory lock por workspace                          |
| "Exatamente um" canal interno depende do provisionamento/backfill: o banco impede DOIS (unique parcial), não impede ZERO                                                                   | Não há API de remoção de canal, então só uma rotina `raw` chegaria a zerar; o service falha alto e claro se acontecer                                          | Surgir CRUD de canais (canais externos, Entrega 7+) → recriação idempotente no boot ou trigger que impeça remover o canal de sistema                                                        |
| Cifra na borda (§7.6) não implementada: os bytes vão em claro para o disco                                                                                                                 | Storage local é do próprio host no MVP; a política já está escrita                                                                                             | Storage compartilhado/S3 ou primeiro dado sensível de vertical (Clinics) → cifrar antes do `put`, com chave separada do JWT                                                                 |
| Upload grava os bytes ANTES da linha: se o banco falhar, sobra órfão no disco                                                                                                              | A ordem inversa deixaria linha apontando para o nada, o que quebra o download do usuário                                                                       | Primeiro cliente com volume real → rotina de varredura de órfãos (chave sem FileObject correspondente)                                                                                      |
| `scanStatus` nunca sai de `pending`: não há scanner ligado                                                                                                                                 | O ESTADO existe desde o início, como a política exige; ligar o scanner é integração                                                                            | **Entrega 9.2**: canal externo real chega, então o scanner deixa de ser opcional                                                                                                            |
| `contact.updated` e `task.completed` estão no enum de webhooks mas não são emitidos                                                                                                        | Enum espelha a allowlist do outbox; emissão é de uma linha por service                                                                                         | Antes de anunciar webhooks a clientes                                                                                                                                                       |
| AuditLog cobre 4 de 11 entidades da allowlist (falta update de contact/company/task e RBAC restante)                                                                                       | Allowlist pronta; ligar cada service é mecânico                                                                                                                | Antes de vender auditoria como recurso / auditoria externa                                                                                                                                  |
| `CryptoService` sem versionamento de chave: rotacionar `TOKEN_ENCRYPTION_KEY` torna `secretCipher` indecifrável                                                                            | Chave única no MVP                                                                                                                                             | Política de rotação de segredos → prefixo de versão no payload cifrado                                                                                                                      |
| `WorkspaceThrottleGuard` desliga com `NODE_ENV=test` e guarda estado em memória                                                                                                            | Simplicidade; instância única                                                                                                                                  | Preview/CI expostos ou multi-instância → flag própria + Redis                                                                                                                               |
| Worker pg-boss não é exercitado por teste (stub no Jest; e2e com DISABLE_JOBS)                                                                                                             | ESM puro no runner CJS; worker não roda em teste por design                                                                                                    | Smoke test com boss real contra o Postgres de teste no CI                                                                                                                                   |
| Erro de TIPO em arquivo `.spec.ts` pode passar localmente e falhar no CI: o `nest build` compila só `src` sem specs, e o cache do ts-jest mascara a recompilação                           | O CI (sem cache) pega — foi assim que o spec do CsrfOriginGuard apareceu quebrado depois do push                                                               | Segunda ocorrência de CI vermelho por tipo em spec → adicionar um `typecheck` que inclua specs ao script de verificação local                                                               |
